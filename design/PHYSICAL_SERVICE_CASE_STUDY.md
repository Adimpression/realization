# Physical Service Environments as Terminal Encoding of Cross-Domain Design Mediation

Physical service environments are not composed primarily of digital components. They are composed of **space, sequence, signage, counters, queues, documents, staff roles, and service rituals**. These are not the theory's primitive categories; they are terminal encodings of deeper interaction obligations inside a physical service system.

---

# I. Mapping Form

The correct derivation is:

[
O \rightarrow I \rightarrow T \rightarrow V \rightarrow G \rightarrow E_{PS}
]

Where:

* (O) = user objective
* (I) = service-user intent
* (T) = task morphology
* (V) = interaction invariant
* (G) = interaction obligation
* (E_{PS}) = physical-service embodiment

Physical service artifacts are therefore **not selected directly from objectives**.

They are selected from **interaction obligations**.

---

# II. Physical Service Artifact Families as Encodings

## 1. Orientation Artifacts

Orientation artifacts include exterior markers, directional signage, zone labels, landmarks, floor markings, maps, and destination counters.

### Upstream derivation

[
\text{Objective} \rightarrow \text{locate / navigate / verify arrival} \rightarrow \text{wayfinding obligation} \rightarrow \text{orientation artifact}
]

### Use when the required obligation is:

* reveal where to go
* distinguish destinations
* preserve orientation across movement
* reduce staff-dependent wayfinding
* show arrival, waiting, and service zones

### Artifact mapping

| Interaction obligation           | Physical-service artifact            |
| -------------------------------- | ------------------------------------ |
| Reveal destination               | Directional sign                     |
| Mark current location            | Zone label / floor marker            |
| Expose route through facility    | Map / route board                    |
| Distinguish service endpoints    | Counter marker / door marker         |
| Confirm that the user arrived    | Service-name placard / check-in sign |

### Theory condition

Use orientation artifacts when:

[
I \in {\text{locate}, \text{navigate}, \text{verify}}
]

and the service depends on successful movement through physical space.

---

## 2. Queue and Flow-Control Artifacts

Queue and flow-control artifacts include single-line queueing, numbered tickets, lane dividers, priority lanes, waiting zones, and call-forward displays.

### Upstream derivation

[
\text{Objective} \rightarrow \text{wait / progress / preserve fairness} \rightarrow \text{flow-control obligation} \rightarrow \text{queue artifact}
]

### Use when the required obligation is:

* preserve order
* reduce ambiguity about sequence
* expose expected waiting behavior
* separate normal flow from exception flow
* handle variable arrival rates without chaos

### Artifact mapping

| Interaction obligation          | Physical-service artifact             |
| ------------------------------- | ------------------------------------- |
| Preserve fair order             | Single queue                          |
| Decouple arrival from service   | Numbered token / ticket               |
| Separate priority traffic       | Priority lane                         |
| Show where to wait              | Waiting zone / floor boundary         |
| Advance the next customer       | Call-forward display / staff callout  |
| Separate exception handling     | Help desk / exception lane            |

### Theory condition

Use queue and flow-control artifacts when:

[
T \in {\text{sequential}, \text{branching}, \text{interrupt_driven}}
]

and service access must be regulated under arrival variability.

---

## 3. Encounter Artifacts

Encounter artifacts include the service desk, counter surface, transaction tray, verification surface, seated consultation point, and shared viewing plane.

### Upstream derivation

[
\text{Objective} \rightarrow \text{inspect / present / verify / exchange} \rightarrow \text{encounter obligation} \rightarrow \text{service encounter artifact}
]

### Use when the required obligation is:

* create a bounded interaction moment
* support exchange of documents or goods
* support identity verification
* preserve privacy or audibility as needed
* give both parties a shared interaction frame

### Artifact mapping

| Interaction obligation      | Physical-service artifact     |
| --------------------------- | ----------------------------- |
| Bounded transaction point   | Counter / desk                |
| Shared document inspection  | Flat viewing surface          |
| Secure handoff              | Pass-through tray             |
| Short advisory interaction  | Standing counter              |
| Longer advisory interaction | Seated consultation station   |
| Partial privacy             | Partition / acoustic boundary |

### Theory condition

Use encounter artifacts when:

[
I \in {\text{inspect}, \text{verify}, \text{modify}, \text{coordinate}}
]

and a service exchange must be bounded in space and role.

---

### Artifact mapping

[
I \in {\text{confirm}, \text{verify}, \text{recover}}

* support correction after an error
* resolve missing information
* separate exception traffic from the normal path
* let users resume without restarting everything
* preserve dignity under failure

### Artifact mapping

| Interaction obligation         | Physical-service artifact      |
| ------------------------------ | ------------------------------ |
| Resolve local confusion        | Help desk                      |

### Theory condition

[
I \in {\text{recover}, \text{verify}, \text{coordinate}}
]

and error cannot be fully prevented.

# IV. Reverse Index: From Task Morphology to Physical-Service Structure

## One-shot service task

Use:

* one destination
* one queue or no queue
* one encounter point
* one receipt or confirmation

Avoid:

* branching signage
* unnecessary intermediate stations

---

## Sequential service task

Use:

* ordered stations
* explicit next-step signage
* progress/status feedback
* re-entry markers between stages

Use when:

[
T = \text{sequential}
]

and order is mandatory.

---

## Branching service task

Use:

* triage point
* clearly differentiated lanes
* visible rule-based routing
* help desk for uncertainty

Use when:

[
T = \text{branching}
]

and users may follow different service paths.

---

## Interrupt-driven service task

Use:

* recallable tokens
* pause/resume artifacts
* exception handling point
* audible and visual interruption signals

Use when:

[
T = \text{interrupt_driven}
]

and the service flow may be paused by missing documents, delays, or changed conditions.

---

# V. Artifact Choice Rules

## Rule 1: Single queue vs multiple queues

Use a **single queue** when fairness, predictability, and load balancing matter more than visible service differentiation.

Use **multiple queues** only when service classes are meaningfully distinct and visible routing is necessary.

Formal condition:

[
\text{SingleQueue} \iff Priority=\text{fair order} \land ServiceVariation=\text{low}
]

[
\text{MultiQueue} \iff ServiceClasses=\text{distinct} \land RoutingNeed=\text{high}
]

---

## Rule 2: Numbered ticket vs standing line

Use a **numbered ticket** when waiting time is long, movement freedom matters, or interruptions are common.

Use a **standing line** when progression is short, linear, and continuously visible.

Formal condition:

[
\text{TicketedFlow} \iff WaitTime=\text{non-trivial} \lor Interruptions=\text{likely}
]

---

## Rule 3: Counter vs consultation station

Use a **counter** for short, high-throughput, lower-complexity interactions.

Use a **consultation station** when privacy, explanation, or extended review is required.

Formal condition:

[
\text{ConsultationStation} \iff Complexity=\text{high} \lor Privacy=\text{high}
]

---

## Rule 4: Receipt vs visible state only

Use a **receipt or stub** when later proof, recovery, or continuation is required.

Use **visible immediate state only** when the interaction ends fully in the moment.

Formal condition:

[
\text{ReceiptRequired} \iff Recoverability=\text{required} \lor ContinuityAcrossTime=\text{required}
]

---

## Rule 5: Help desk vs inline staff explanation

Use **inline explanation** when uncertainty is local and brief.

Use a **help desk or exception point** when ambiguity can reroute the flow or block progress.

Formal condition:

[
\text{ExceptionDesk} \iff FailureMode=\text{flow-blocking} \lor Resolution=\text{multi-step}
]

---

# VI. General Decision Procedure

For any physical service objective:

## Step 1: Decompose the objective into intents

Example:

[
O=\text{obtain a municipal permit}
]

becomes:

[
I={\text{locate}, \text{inspect}, \text{enter}, \text{verify}, \text{confirm}, \text{recover}}
]

---

## Step 2: Determine task morphology

[
T={\text{sequential}, \text{branching}, \text{interrupt_driven}}
]

---

## Step 3: Derive invariants

[
V={\text{visibility}, \text{legibility}, \text{feedback}, \text{constraint}, \text{recoverability}}
]

---

## Step 4: Convert invariants into obligations

* the next station must be visible
* missing documentation must be detected before late-stage service
* waiting state must be perceptible
* exception recovery must not destroy progress already made

---

## Step 5: Select physical-service artifacts

* directional signage
* triage desk
* numbered ticket
* service counter
* receipt or claim stub
* exception desk

---

# VII. Canonical Derivation Example

## Example: “A visitor wants to complete government service intake”

[
O=\text{complete intake}
]

[
I={\text{locate}, \text{wait}, \text{enter}, \text{verify}, \text{confirm}, \text{recover}}
]

[
T=\text{sequential + branching}
]

[
V={\text{visibility}, \text{state_awareness}, \text{constraint}, \text{feedback}, \text{recoverability}}
]

Physical-service encoding:

* exterior and interior wayfinding signs
* triage point to route visitors correctly
* numbered ticket for queue identity
* main intake counter
* document ledge for shared verification
* acknowledgment receipt
* exception desk for missing documents

---

# VIII. The Physical-Service “Compiler” Rule

A physical service artifact should be chosen only when the following chain is valid:

[
\text{Artifact} \Leftarrow \text{Embodiment} \Leftarrow \text{Obligation} \Leftarrow \text{Invariant} \Leftarrow \text{Task Morphology} \Leftarrow \text{Intent} \Leftarrow \text{Objective}
]

So the design question is never:

> “Should we add another counter?”

It is:

> “Does the objective produce a bounded verification-and-commitment obligation that requires a dedicated encounter point?”

If yes, use a counter or consultation station.

---

# IX. Final Statement

Physical service artifacts are the **spatial and procedural embodiment vocabulary** of the theory.

The theory does not say:

[
\text{Visitor wants X} \rightarrow \text{Use artifact Y}
]

It says:

[
\text{Visitor objective}
\rightarrow
\text{service intent}
\rightarrow
\text{task morphology}
\rightarrow
\text{interaction invariant}
\rightarrow
\text{interaction obligation}
\rightarrow
\text{physical-service artifact}
]

This is the proper bridge from abstract service purpose to concrete spatial and procedural form.
