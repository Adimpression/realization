It does not always decompose the prompt. The workstation uses a staged router: shell shortcut first, heuristic multi-skill composition second, heuristic single-skill invocation third, and the LLM tool loop last. The main entry is [`workstation/runtime_core/src/workstation/runtime/core/session.py`](../workstation/runtime_core/src/workstation/runtime/core/session.py).

1. `prompt_workstation_session()` loads the session, normalizes the raw prompt into a `TaskBoundaryContract`, writes `TASK.md` and `TASK_CONTRACT.json`, updates message history, and appends receipts. This is the common entry for every turn. [`session.py`](../workstation/runtime_core/src/workstation/runtime/core/session.py) [`task_contract.py`](../workstation/foundation_host/src/workstation/foundation/host/task_contract.py)

2. It first tries a natural-language shell shortcut. If the prompt looks like an import/export or similar built-in shell utility, the turn ends here and no skill planning happens. [`session.py`](../workstation/runtime_core/src/workstation/runtime/core/session.py)

3. If workflow composition is allowed, it asks `preferred_workstation_skill_composition_plan()` whether the prompt looks like a pipeline. That planner detects multi-step intent, splits the prompt into clauses, shortlists candidate skills, and tries to assign one skill per clause. [`session.py`](../workstation/runtime_core/src/workstation/runtime/core/session.py) [`skill_composition_planning.py`](../workstation/skills_planning/src/workstation/skills/planning/skill_composition_planning.py)

4. The planner wires steps in two ways. Prompt-local values become `root_inputs` or `root_references`, and later steps get bindings from prior step outputs by matching canonical leaf paths between skills. That matching logic is in `_candidate_mappings_from_prior_steps()`. [`workstation/skill_composition_planning.py:494`](workstation/skill_composition_planning.py#L494) [`skill_composition.py:57`](skill_composition.py#L57)

5. If a plan is found, the session converts it into a `BlendWorkflowPlan` and dispatches `ws.workflow.run` or `ws.skill.compose`. The capability dispatcher is the single gateway for all workstation tool calls. [`session.py`](../workstation/runtime_core/src/workstation/runtime/core/session.py) [`blend_workflow.py`](../blend_workflow.py) [`capabilities.py`](../workstation/runtime_core/src/workstation/runtime/core/capabilities.py)

6. `_execute_workflow()` builds operator providers from the attached skill store plus any shared workstation capabilities, then resolves each workflow step to a concrete operator and target under the current workstation context. [`workstation/capabilities.py:1994`](workstation/capabilities.py#L1994) [`workstation/capabilities.py:1527`](workstation/capabilities.py#L1527) [`blend_workflow_execution.py:75`](blend_workflow_execution.py#L75)

7. `execute_blend_workflow()` hands the resolved steps to `execute_skill_composition_plan()`. This is the actual wiring engine: it evaluates `run_if`, constructs each step payload from root values, constants, or prior step output leaves, applies mappers, invokes the step, and records emitted leaves so downstream steps can consume them. [`blend_workflow_execution.py:174`](blend_workflow_execution.py#L174) [`skill_composition.py:911`](skill_composition.py#L911)

8. Each skill step eventually goes through `_skill_invoke()`. That resolves the skill title against the attached skill store or builtin skills, merges explicit payload with prompt-derived payload, derives required delegation, and either asks for approval or prepares a nested invocation. [`workstation/capabilities.py:2353`](workstation/capabilities.py#L2353) [`workstation/skill_invocation.py:164`](workstation/skill_invocation.py#L164) [`workstation/skill_invocation.py:326`](workstation/skill_invocation.py#L326)

9. The nested invocation is a real governed runtime call, not a direct function jump. `_skill_invoke()` bootstraps a fresh `SystemState`, creates a nested `BSSCController` with `llm_policy="off"`, injects delegated mounts/capabilities, then runs `execute_function_artifact()` for abilities or `artifact_answer_text()` for knowledge artifacts. [`workstation/capabilities.py:2586`](workstation/capabilities.py#L2586) [`main.py:2727`](main.py#L2727)

10. When the workflow finishes, it chooses `final_output_step` or falls back to the last successful step, renders the answer, aggregates delegation/results across steps, and persists the workflow plan/run. [`blend_workflow_execution.py:297`](blend_workflow_execution.py#L297) [`blend_workflow_execution.py:394`](blend_workflow_execution.py#L394)

11. If no multi-step plan is found, the workstation tries the single-skill shortcut. `preferred_workstation_skill_invocation_plan()` shortlists one strong skill match and derives obvious arguments from literals in the prompt such as mounts, paths, URLs, text, and numbers, then calls `ws.skill.invoke` directly. [`session.py`](../workstation/runtime_core/src/workstation/runtime/core/session.py) [`direct_composition.py`](../workstation/skills_core/src/workstation/skills/core/direct_composition.py)

12. If both heuristic paths fail, `run_workstation_openai_turn()` starts the OpenAI-compatible tool loop. The system prompt tells the model to prefer `ws.skill.invoke`, `ws.skill.compose`, and `ws.workflow.run`; tool calls are executed through the same dispatcher above, so the LLM path still lands on the same skill/workflow runtime. [`session.py`](../workstation/runtime_core/src/workstation/runtime/core/session.py) [`llm_driver.py`](../workstation/runtime_core/src/workstation/runtime/core/llm_driver.py)

The shortest summary is: prompt -> router -> maybe build workflow plan -> resolve step operators -> bind step inputs from prompt and prior outputs -> invoke each skill in a nested governed runtime -> choose final step output -> return assistant text.
